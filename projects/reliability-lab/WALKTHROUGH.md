# 技术讲解与自验证手册

不是帮你背一份虚构履历，而是让你能追问这套系统并用实验回答。

## 三分钟讲解结构

1. **问题**：AI 工作流不只会“答案错”，还会超时、暂时失败、永久异常和“已提交但没收到应答”。执行机制应把这些情况分开。
2. **方案**：固定 5 节点工作流；并发有界；暂时错误重试、永久错误停止；预算包含排队；保存成功节点；本地副作用用幂等账本。
3. **证据**：同 seed 同故障清单，四策略对照、六场景、5 次重复；原始 JSON 可重算。无故障和永久错误等不利结果也保留。
4. **局限**：合成 I/O、本地 SQLite，不是模型推理、生产系统或分布式 exactly-once。代码 AI 辅助完成，个人贡献如实说明。

## 应该能现场回答

- baseline 为什么延迟有时更低？因为它失败早退，不能据此宣称用户得到更好结果。
- 为什么 retry 可能重复提交？操作已经写入，但应答丢失，下一次又写入。
- 为什么本地幂等不等于远程 exactly-once？唯一约束和提交事务只覆盖同一 SQLite 数据库，没有跨外部系统事务。
- checkpoint 为什么不能随便复用？模型/负载/配置或代码语义改变，旧输出可能不再有效；当前绑定配置与版本并保留源代码哈希。
- timeout 为什么不总是收益？真实任务可能只是慢但会成功；终止重试可能浪费已完成计算。这里“慢一次”是受控故障，不能直接外推。
- 为什么端到端预算包含排队？用户从提交就开始等待；高负载导致的排队也是可靠性交付的边界。
- 当前支持什么取消？可取消的 asyncio 合成任务；阻塞插件和忽略取消的远程任务不在证明范围。
- 为什么不用 Ray/Redis/Kafka？当前负载本地、规模小；增加中间件不能替代证明问题和瓶颈。可扩展路线已写，但不冒充已经实现。

## 亲自完成三个小实验

1. 使用相同 seed 比较 ack_loss 的 retry 与 resilient，导出 JSON，数出重复提交。
2. 把工作流预算调小，看哪些任务还在排队就失败；从 events 与 queue_ms 验证。
3. 在 config.py 修改一个公开合成故障阈值，添加测试、重跑到新目录，记录成功率与失败分布的变化。
